**KernelSocket** — это унифицированный кроссплатформенный API для создания сетевых соединений (TCP и UDP) из пространства ядра (ring-0) для операционных систем Windows и Linux.

Проект разработан в рамках курса «Основы проектной деятельности» (ОПД).

---

## Описание проекта и проблематика

Разработка сетевого взаимодействия на уровне ядра (ring-0) — ресурсоемкая задача с высоким порогом входа. Сетевые стеки ядер Windows и Linux имеют фундаментальные архитектурные различия:

- **Windows (Winsock Kernel — WSK):** Базируется на асинхронной модели ввода-вывода. Разработчику необходимо вручную регистрировать NPI-клиента, аллоцировать IRP-пакеты, описывать буферы через списки дескрипторов памяти (MDL) и использовать раздельные таблицы диспетчеризации для TCP и UDP.
- **Linux (Kernel Sockets):** Реализуется через внутренние функции `sock_create_kern` и `kernel_sendmsg`. Хотя концепция ближе к классическим сокетам, малейшая ошибка в выделении памяти или неинициализированная структура (например, `msghdr`) мгновенно приводит к краху системы (Kernel Panic).

**Решение:**
Библиотека **KernelSocket** берет на себя всю низкоуровневую работу с подсистемами ОС и предоставляет разработчику драйверов единый заголовочный файл `ks_api.h`. Он эмулирует привычное синхронное (блокирующее) поведение POSIX-сокетов из user-mode, позволяя писать кроссплатформенный сетевой код для ядра так же легко, как для обычных пользовательских приложений.

### Ключевые возможности и инженерные решения:
- **Полный стек TCP и UDP:** Реализация как Клиентской, так и Серверной логики (поддержка `ksListen` и `ksAccept` для прослушивания входящих соединений внутри ядра).
- **Абстракция асинхронности:** В Windows асинхронные WSK-вызовы «под капотом» оборачиваются в удобные синхронные функции с использованием `KEVENT`, полностью скрывая работу с IRP от конечного пользователя.
- **«Ленивая» инициализация:** Решает архитектурную проблему WSK (требующего указывать роль сокета при создании), позволяя использовать классический паттерн `ksSocket() -> ksBind/ksConnect`.
- **Абсолютная безопасность (Memory & IRQL Safety):** 
  - *В Windows:* Встроена строгая проверка вызова функций на уровне `IRQL == PASSIVE_LEVEL` и автоматическая безопасная работа с памятью через `NonPagedPool`.
  - *В Linux:* Встроена защита от мусорных указателей и переполнения структур ядра.
- **Строгая инкапсуляция:** Использование архитектурного паттерна *Непрозрачный указатель (Opaque Pointer)*. Внутренняя реализация сокета скрыта, что защищает ядро от некорректного вмешательства извне.

## Структура репозитория

Проект имеет строгую архитектуру, разделяющую публичный интерфейс, внутреннюю реализацию и тестовое окружение:

```text
KernelSocket/
├── docs/                           # Документация и генератор Doxygen
│   ├── Doxyfile                    # Конфигурация генератора
│   ├── header.html                 # Пользовательский HTML-заголовок
│   └── doxygen-awesome-css/        # Тема оформления (подключена как git submodule)
│
├── include/                        # Публичный интерфейс (Подключается пользователями)
│   └── ks_api.h                    # Единый API-контракт (Opaque Pointer)
│
├── src/                            # Исходные коды (Внутренняя реализация)
│   ├── linux/                      
│   │   ├── ks_linux.c              # Реализация для Linux (через sock_create_kern)
│   │   └── ks_linux_internal.h     # Приватная структура сокета (инкапсулирована)
│   │
│   └── windows/                    
│       ├── ks_windows.c            # Реализация для Windows (через Winsock Kernel - WSK)
│       └── ks_windows_internal.h   # Приватная структура и функции ленивой инициализации
│
└── test/                           # Тестовое окружение (Точки входа)
    ├── ks_config.txt               # Конфигурация IP/портов для тестов
    ├── user_test.py                # Python-утилита для тестов Ring-3 ↔ Ring-0
    │
    ├── linux/                      
    │   └── module_main.c           # Демонстрационный LKM-модуль (содержит потоки)
    │
    └── windows/                    
        └── driver_entry.c          # Демонстрационный KMDF-драйвер (содержит потоки)
```

### Архитектурные особенности:
- **Инкапсуляция:** Пользовательский код взаимодействует только с файлом `include/ks_api.h`. Внутренние структуры ОС скрыты в файлах `*_internal.h` внутри папки `src/`. Это защищает библиотеку от некорректного использования и случайных BSOD/Kernel Panic.
- **Разделение логики:** Тестовые потоки и точки входа (`DriverEntry` и `module_init`) полностью вынесены в директорию `test/`, оставляя папку `src/` чистой библиотечной реализацией, готовой к экспорту.

## Сборка и запуск (Kernel-to-Kernel)

Демонстрационные драйверы (точки входа `driver_entry.c` и `module_main.c`), запускающие тестовые потоки, вынесены в директорию `test/`.

### Windows (KMDF)
1. Создайте проект **Empty WDM Driver** (или KMDF) в **Visual Studio 2022** (требуется установленный WDK).
2. Добавьте в проект два файла исходного кода:
   - Библиотеку: `src/windows/ks_windows.c`
   - Тестовую точку входа: `test/windows/driver_entry.c`
3. В свойствах проекта перейдите в **Linker -> Input -> Additional Dependencies** и добавьте `netio.lib` (требуется для работы подсистемы WSK).
4. Выберите конфигурацию `Debug | x64` и соберите решение (`Ctrl+Shift+B`).
5. Скопируйте полученный `KernelSocket.sys` на виртуальную машину (ОС должна быть в режиме разработчика: `bcdedit /set testsigning on`).
6. Загрузите драйвер через командную строку от имени Администратора:
   ```cmd
   sc create KernelSocket type= kernel binPath= C:\Путь\К\KernelSocket.sys
   sc start KernelSocket
   ```
7. Логи обмена данными отслеживаются через утилиту **DebugView**. Остановка: `sc stop KernelSocket`.

### Linux (LKM)
Для сборки тестового модуля Linux используется `Makefile`, объединяющий исходники библиотеки и теста.
1. Перейдите в директорию `test/linux/`:
   ```bash
   cd test/linux/
   ```
2. Убедитесь, что в этой папке лежит `Makefile` следующего содержания:
   ```makefile
   obj-m += ks_linux_module.o
   # Указываем пути к точке входа и к реализации API
   ks_linux_module-objs := module_main.o ../../src/linux/ks_linux.o

   all:
   	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
   clean:
   	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean
   ```
3. Выполните сборку модуля:
   ```bash
   make
   ```
4. Загрузите скомпилированный модуль ядра:
   ```bash
   sudo insmod ks_linux_module.ko
   ```
5. Просмотр логов в реальном времени:
   ```bash
   dmesg -w
   ```
6. Выгрузка модуля: `sudo rmmod ks_linux_module`.

## Методология и сценарии тестирования

Проект покрывает расширенную матрицу тестирования, включающую проверку обмена данными локально (`127.0.0.1`) и по сети между разными виртуальными машинами (VPN / Сетевой мост). Тестируются все комбинации для **TCP** и **UDP**.

### Сценарий 1: Kernel ↔ Kernel (Ядро общается с Ядром)
Базовый тест, доказывающий корректность работы сетевого стека внутри ring-0 без участия пользовательского пространства.
* **Локально:** При стандартной сборке `driver_entry.c` / `module_main.c` драйвер запускает 4 системных потока (TCP-сервер, TCP-клиент, UDP-сервер, UDP-клиент). Клиенты подключаются к серверам на `127.0.0.1` и обмениваются эхо-сообщениями.
* **По сети (Кроссплатформенно):** 
  1. На ВМ №1 (например, Linux) в `module_main.c` комментируется код клиентов — ядро работает только как Сервер.
  2. На ВМ №2 (Windows) в `driver_entry.c` комментируется код серверов, а в `ksConnect` / `ksSendTo` вместо `127.0.0.1` вписывается IP-адрес первой ВМ.
  3. Драйверы загружаются, и происходит обмен пакетами между ядрами разных ОС.

### Сценарий 2: User ↔ Kernel (Кросс-уровневое взаимодействие)
Для тестирования связи драйверов с классическими приложениями (ring-3) написана мультитул-утилита на Python: `test/user_test.py`.

**Вариант А (User -> Kernel): Программа стучится в Ядро**
1. Соберите и загрузите драйвер ОС, оставив включенными только **серверные потоки** (слушают порты `9000` и `9001`).
2. Запустите скрипт: `python test/user_test.py`.
3. Выберите режим **КЛИЕНТ**. Скрипт отправит TCP и UDP запросы в ядро ОС и выведет полученный от драйвера ответ в консоль.

**Вариант Б (Kernel -> User): Ядро стучится в Программу**
1. Запустите скрипт: `python test/user_test.py`.
2. Выберите режим **СЕРВЕР** (скрипт займет порты `9000` и `9001` и перейдет в режим ожидания).
3. Соберите и загрузите драйвер ОС, оставив включенными только **клиентские потоки**.
4. Ядро подключится к Python-скрипту, обменяется данными, и результат отобразится в логах ядра (`DebugView` / `dmesg`).

### Решение частых сетевых проблем при тестировании
Если пакеты не проходят между виртуальными машинами (или между Хостом и ВМ), проверьте две вещи:
1. **Брандмауэр (Firewall):** По умолчанию ОС блокируют входящие запросы на нестандартные порты. 
   - *Windows:* Разрешите порты через PowerShell: 
     `New-NetFirewallRule -DisplayName "KS" -Direction Inbound -LocalPort 9000,9001 -Protocol TCP -Action Allow` (и аналогично для UDP).
   - *Linux (Ubuntu/Debian):* Откройте порты через UFW: `sudo ufw allow 9000/tcp && sudo ufw allow 9001/udp`.
2. **Изоляция виртуальных сетей (NAT):** IP-адрес `127.0.0.1` работает только внутри одной ОС. Если ВМ настроена в режиме `NAT`, она невидима снаружи. Переключите сетевой адаптер гипервизора (VirtualBox/VMware) в режим **«Сетевой мост» (Bridged Adapter)** или настройте **Проброс портов (Port Forwarding)**.

## Документация (Doxygen)

Проект содержит исчерпывающую документацию, сгенерированную на основе комментариев в исходном коде. Документация оформлена с использованием современной пользовательской темы **Doxygen Awesome CSS**, что делает её визуально приятной, удобной для чтения и навигации.

### Что включает в себя документация:
- **Справочник API:** Подробное описание всех функций из `ks_api.h` (параметры, возвращаемые значения).
- **Предупреждения о BSOD / Kernel Panic:** Описание критических требований к вызову функций (например, необходимость вызова строго на уровне `IRQL == PASSIVE_LEVEL` и использование памяти типа `NonPagedPool`).
- **Внутренняя реализация:** Задокументированные исходные файлы `ks_windows.c` и `ks_linux.c` с описанием принятых архитектурных решений (например, использование паттерна «Ленивая инициализация» для WSK).

### Инструкция по генерации:
Для самостоятельной генерации документации вам потребуется установленный пакет [Doxygen](https://doxygen.nl/).

1. Перейдите в директорию с документацией:
   ```bash
   cd docs
   ```
2. Запустите генератор, используя подготовленный конфигурационный файл `Doxyfile`:
   ```bash
   doxygen Doxyfile
   ```
3. После завершения процесса откройте сгенерированную главную страницу в любом современном веб-браузере:
   - **Путь:** `html/index.html`

*(Примечание: директория `doxygen-awesome-css` с файлами стилей темы должна находиться в папке docs, так как конфигурация ссылается именно на неё).*
